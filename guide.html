01

What this platform is, and how it works

Two minutes of context, so everything below makes sense.

One folder, no server

Every diagram is its own HTML file. Open index.html and everything loads. It runs on file:// - no Node, no Python, no internet.

Everything is generated, not hand-made

The diagram data, the code links, the index and the code mirror are all built by tools/*.mjs scripts. So the content never drifts away from the real code.

One diagram, one idea

Each page teaches a single thing: the request path, the proxy trap, the transaction boundary, the readiness probe. One page is one mental model. That is why there are 21 pages and not one big one.

Real code, real responses

The Book Store source is mirrored inside the page, and the API responses were captured from one live run - 18 queries vs 1 for the N+1 case, 201/409 for the transaction modes. All of it with proof.

Everything stays in your browser

Quiz scores, notes and progress all live in localStorage, in this browser only. Nothing is uploaded. One click on the Progress tab resets it.

Works offline, and prints

The theme toggle and the Print button both work, so you can export the whole revision as a PDF.

02

First step - where to begin

The order matters. The sequence below exists because the later diagrams make no sense without the earlier ones.

  1. Open index.html and stay on the Home tab You will see the stats at the top (21 diagrams, 196 nodes, 61 views...) and a "Start here: the roadmap" card below. Click that card.
  2. Read the roadmap diagram - 15 minutes Spring_Boot_Roadmap.html shows the whole journey in six parts. Do not go into detail yet. Just build a map of which topic comes when.
  3. Go to the Tracks tab in the hub There are six tracks: Foundations, How it works, Data and persistence, Security, Running it, Hardening. Inside a track the diagrams are already in order - read from top to bottom. Each track has its own progress bar.
  4. Your first real diagram: Request Path The full trip from browser to SQL. This is the diagram that makes the rest start to make sense. Hover a node and read its passport.
  5. Press Q after every diagram The quiz only shows questions for that diagram. A wrong answer comes with an explanation, a "Walk through" and a source link - jump straight to the code from there.
  6. Write notes with N Whatever you keep forgetting, write a note on that node. Notes are saved in the browser together with your progress - they do the same job when you revise for an interview.
Do not open all 21 diagrams at once. Finish one track, clear its quiz, then start the next one. Otherwise you get information overload and you retain nothing.

04

Anatomy of a diagram page

Whatever diagram you open, the layout is always the same. Learn it once and it works on all 21 pages.

Hover / Tab = semantic passport

Hover any node or relationship (or move focus to it with Tab) - a card opens with a summary and three specific points. This is material to understand, not material to memorise.

Concept chips = sideways jump

If the passport shows concept chips, this idea also appears in other diagrams. Click a chip and that concept opens from that angle.

Code chips = straight to the source

The file chip in the passport shows the real code for that node - in the page viewer, not in a new tab.

Guided views + Present mode

Every diagram has 0-3 guided views. Press P and the diagram takes the whole screen: a soft light stays on the current step while the rest falls away, and a rail on the right carries the narration and the passport for every node in that step. →, Space or P moves forward, ← moves back, Home and End jump to the ends.

The toolbar on top

Search, Walk through, Code lab, Quiz, Notes, Present, Tour, Terms, Debug, Interview, Hub - all one click away. Every button also shows its shortcut. On your first visit each page walks you through itself once - a spotlight card that points at the diagram, the passport, the toolbar and the shortcuts - and the Tour button (or U) brings that walk back whenever you want it.

Deep links

Any page can also be opened like this: ...html#node=query101 (focus a specific node) or ...html#view=quiz (open the quiz panel right away). Keep links like that in your notes or bookmarks.

Keyboard first: you do not need the mouse. Tab moves from node to node, Enter opens the detail, Esc closes it. Every node also has an ARIA label for screen reader users.

06

Code lab - connect theory to real code

This is where a diagram turns into proof. Shortcut: C.

Code lab panel (C)

The diagram overview, its shared concepts, its guided views, and the list of "Runnable code in Book Store" - each file with an "in page" badge. Below that, the Walk through and captured response buttons.

Source viewer

Every code link opens on the same page: the file role badge, path and summary at the top; then the structure outline (class, method and field chips) that jump straight to a line when clicked; then the whole file with syntax highlighting; and the explained lines together with their explanation.

Walk through (walkthrough)

The N+1 and Transactions diagrams have a "Walk through" button in the toolbar. Each step shows the source next to the database query count or transaction report from that moment. Watch step by step how 1 query becomes 18.

Captured responses (evidence)

These are not screenshots. They are real HTTP responses captured from one live run of the app: join-fetch = 1 query with a byte-identical payload, mode=required / requires-new = 201, mode=poison = 409 rollback.

One guarantee: no code reference ever shows a raw text dump. If a file mirror is missing, the viewer tells you which script to run (node tools/build-code-viewer.mjs) - you are never sent somewhere else.

08

Progress, theme, print - set it up your way

Progress tab

A table per diagram: opened or not, how many quiz answers are right, how many notes, and one bar that adds all three together (34% opened + 33% quiz + 33% notes). The Tracks tab has a progress bar above each track.

Reset all progress clears everything at once - at the bottom of the Progress tab.

Everything is local

sbk.v1.progress, sbk.v1.quiz, sbk.v1.notes - three keys, all in browser localStorage. No account, no server call. Your progress does not move to another browser or machine.

Theme

The Theme button in the header switches dark and light. Your choice is saved in sbk.theme and stays that way next time. Light for reading at night, dark during the day - whatever suits your eyes.

Print / PDF export

The header Print button (or Print / export this page in the Progress tab) opens the browser print dialog - make a PDF and keep it for revision before an interview.

10

Best practices - how to get the most out of it

These habits are what separate "I read this once" from "I remember this in the interview".

1. Think first, then hover

Before you hover a node, spend five seconds guessing the answer yourself. Active recall raises retention many times over. Use the hover card only to confirm your answer.

2. A quiz after every diagram, no exceptions

Reading a diagram feels comfortable; only the quiz shows the gap. Always read the explanation for a wrong answer - that is where the real misunderstanding shows up.

3. Turn notes into interview prep

Write each note as if you were explaining it to yourself a week later: "difference between REQUIRED and REQUIRES_NEW - the outer one is suspended, so..." Those notes become a personal cheat sheet later.

4. Move sideways through concept chips

Whenever you see a concept chip in a passport, click it. Seeing one trap from three different angles is what actually understanding the concept means. The Concepts tab does the same job.

5. Start from the symptom in the debug table

Stop memorising. When you see an error, open T and search for the exception name. You get both the cause and the fix. This replaces the habit of googling errors.

6. Use the interview bank as a mock test

Do not read the answer straight away. Hear the question, talk for 60 seconds, then press "Show answer", then score yourself. Keep the order junior → mid → senior.

7. Actually run the Book Store

Theory stays with you only until you run the code. Curl the N+1 endpoint yourself and watch the query count. Muscle memory takes time, so do not skip this step.

8. Treat the walkthrough as proof

The diagram says "1 query becomes 18" - the walkthrough shows the same thing with a live query count. Seeing both at once makes the concept permanent.

9. Finish one track at a time

Jumping from the middle of one track to another is the biggest mistake. Take a track's progress bar to 100% before you open the next one.

10. Spaced repetition - come back after a week

Seven days after finishing a track, open it again and only take the quiz. Update the note on anything you still forget. The Progress tab shows where you are weak.

11. Take a printout or PDF

Two days before an interview, export everything to a PDF and read only your notes and missed quiz questions. That works better than a screen.

12. Say each concept "in one line"

Open the Concepts tab and say each concept in one line, in your own words. Whatever you cannot do, read again. This is the fastest self-test there is.

11

A 30-day study plan

A suggested order for fitting six tracks plus practice and hands-on work into one month. Go at your own speed, but do not change the order.

DAY 1-3
Foundations (3 diagrams) Roadmap, container and startup. The vocabulary you pick up here (bean, context, lifecycle) is used everywhere. End day 3 with the quiz at 100%.
DAY 4-8
How it works (5 diagrams) Request path, AOP proxy, layers, configuration precedence, auto-configuration. This is the most important track - it is the core of the interview.
DAY 9-13
Data and persistence (4 diagrams) Data model, N+1, Transactions, Caching. Run the N+1 and Transactions walkthroughs - that is the proof for this track.
DAY 14
Security (1 diagram) Security + JWT. A small track, but you should understand the filter chain. Also read the security entries in the debug table.
DAY 15-18
Running it (4 diagrams) Observability, async/scheduling, messaging (outbox), deployment. This is where the "what actually happens in production" mindset forms.
DAY 19-22
Hardening (4 diagrams) Testing slices, AntiPatterns, migration, and the roadmap again. Read AntiPatterns most carefully - the wrong things are there on purpose.
DAY 23-25
Book Store hands-on Run the project, curl the N+1 endpoint, see the 409 from mode=poison yourself, check the transaction probe. Keep the code lab open alongside it with C.
DAY 26-27
Quiz sweep - 128 items Take every diagram's quiz again from the Practice tab. Update the note for anything you miss. Target: 80%+ on every diagram.
DAY 28-29
Debug table + Interview bank Read the 47 debug entries once, symptom by symptom. Then the 74 interview questions - junior to senior, without looking at answers.
DAY 30
Revision - notes + PDF Read all your notes once, redo the missed quiz questions, export the PDF. You are ready now.

The Book Store project - how to run it

Alongside the diagrams there is a working Spring Boot 3 application that contains the same deliberate mistakes the diagrams teach.

  1. Open the folder: bookstore/ The README maps every node id to its diagram and its file. The only requirement is a JDK.
  2. Run the tests: test.cmd The Maven wrapper is committed, so it works even if mvn is not on your PATH. Expected: 15 tests, 0 failures.
  3. Start the app: run.cmd The jar is built and starts on http://localhost:8080. Health check: /actuator/health.
  4. See the N+1 for yourself /api/catalog/books/naive vs /api/catalog/books/join-fetch - the payload is the same, the query count is not (18 vs 1).
  5. Try the transaction modes mode=required → 201, mode=requires-new → 201, mode=poison → 409 rollback. The same numbers captured in the evidence panel.
  6. Keep it open next to the diagram Diagram on one side, terminal on the other. What the diagram says is what happens in the terminal - that is where the confidence comes from.
Mistakes left in the project on purpose: self-invocation (advice bypass), N+1 select, rollback-only trap, forgetting to evict the cache, catch-all exception handler, mutable entities. Do not treat them as bugs - they are teaching material. Each one comes with its own "fix".
13

Common mistakes (and their fixes)

ProblemFix
"I opened everything and remember nothing" You read it, but you did not recall it. Always take the quiz after reading, and write a note.
I clicked a code link and got a text dump That was a bug and it is fixed - every link now opens in the page viewer. If you ever see it, run node tools/build-code-viewer.mjs.
My progress is missing Open the Progress tab. If this browser has no data at all, you were in another browser or in incognito - localStorage belongs to one browser.
The app will not start Port 8080 is busy. Stop the old process, then run run.cmd again. Or just use spring-boot:run.
The code sample looks out of date Run node tools/audit-links.mjs - it compares every mirrored file with the original byte for byte and names the exact file if it is stale.
"Which diagram comes first?" The Tracks tab (key 2). The Library tab is for browsing only, not for order.
The shortcuts do not work Focus is in an input box. Press Esc, or click outside it.
Are diagrams alone enough for an interview? Diagrams give you understanding, not phrasing. Practise out loud with the interview bank (I).
14

Advanced - for people who will change the content

If you are only studying, skip this section. If you want to customise this resource, start here.

Everything comes from tools/

build-content-index.mjs (index) → build-code-viewer.mjs (code mirror) → enhance-hover.mjs (diagram tags). The order matters.

Re-capturing the evidence

capture-evidence.mjs starts the app itself, first stopping whatever old process is on port 8080, asserts the responses, and confirms it shut down. After that you must run build-traces.mjs.

Validation commands

audit-links, probe-code-viewer, probe-code-lab, probe-hover, probe-kit, probe-hub - all run as node tools/<name>.mjs.

How to add a new diagram

Build the HTML first, then rebuild content-index.js, then run enhance-hover.mjs. The audit checks on its own that every node id, edge and code link is right.

Do not edit these by hand: evidence.js, code-source.js, content-index.js and the base diagrams - they are generated and the next run will overwrite them.
